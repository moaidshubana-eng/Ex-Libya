# Ex-Libya — منصّة الصرف الليبية

خدمة الخلفية (API) لمنصة إدارة الخزينة والعملاء وتداول العملات لشركة صرافة في
السوق الليبي. يغطي هذا الإصدار: الأساس (خزينة، عملاء، أسعار صرف)،
**محرك التداول** فوقه (دفتر صفقات بقفل سعر مؤقت، اعتماد تلقائي فوري بلا فحص
حدود، واحتساب هامش ربح/خسارة تلقائي مقابل سعر السوق الموازي يُرحَّل محاسبيًا
عند التنفيذ، وتسوية تلقائية على رصيد الخزينة)، **وحدة محاسبية** بدفتر أستاذ
مزدوج القيد (قائمة المركز المالي وقائمة الدخل)، **بوابة واتساب** (WhatsApp
Business Cloud API) لاستقبال استفسارات الأسعار آليًا وبثّ تحديثاتها وتأكيد
الصفقات، **ومصادقة ثنائية (TOTP)** إلزامية على أخطر الإجراءات في النظام (نشر
سعر) — مع البنية التحتية المشتركة (مصادقة، صلاحيات، سجل تدقيق) التي تخدم كل الوحدات.

للاطلاع على التصميم المعماري الكامل والخطة الزمنية على مستوى المنتج، راجع وثيقة
التصميم التي سبقت هذا التنفيذ.

## التقنية المستخدمة

| الطبقة | الاختيار | السبب |
|---|---|---|
| الخادم | NestJS + TypeScript | معماريته المعيارية (Modules) تطابق تصميم "أحادي معياري" الذي اعتُمد: كل وحدة أعمال (خزينة، عملاء، أسعار) معزولة، وقابلة للفصل لاحقًا إلى خدمة مستقلة. |
| قاعدة البيانات | PostgreSQL + Prisma | دقة عشرية موثوقة للقيم المالية (`Decimal`)، هجرات (migrations) صريحة ومراجَعة، وسجل تدقيق قابل للاستعلام. |
| المصادقة | JWT + Argon2 + TOTP | كلمات مرور مُجزَّأة بخوارزمية Argon2id، جلسات بلا حالة (stateless)، ومصادقة ثنائية (RFC 6238) لأخطر الإجراءات — سرّها مشفّر وقت السكون (AES-256-GCM) بمفتاح خادم منفصل، لا مُجزَّأ، لأنه يجب فكّ تشفيره لاحقًا للتحقق. |
| التوثيق | Swagger/OpenAPI | توثيق تفاعلي تلقائي على `/api/docs` لكل نقطة نهاية. |

## البدء السريع

```bash
# 1) تشغيل قاعدة بيانات PostgreSQL محلية
docker compose up -d

# 2) تثبيت الحزم
npm install

# 3) إعداد متغيرات البيئة
cp .env.example .env

# 4) إنشاء الجداول وتوليد عميل Prisma
npm run prisma:migrate

# 5) تعبئة بيانات تجريبية (فروع، عملات، مستخدمون، عملاء، أول سعر صرف)
npm run prisma:seed

# 6) تشغيل الخادم في وضع التطوير
npm run start:dev
```

الخادم يعمل افتراضيًا على `http://localhost:3000`، والتوثيق التفاعلي على
`http://localhost:3000/api/docs`.

### بيانات دخول تجريبية (بعد التعبئة)

كلمة المرور لكل الحسابات: `ChangeMe123!` — **غيّرها فورًا في أي بيئة غير محلية.**

| الدور | البريد الإلكتروني |
|---|---|
| ADMIN | admin@exlibya.ly |
| TREASURY_MANAGER | treasury.manager@exlibya.ly |
| TELLER | teller@exlibya.ly |
| COMPLIANCE_OFFICER | compliance@exlibya.ly |
| CUSTOMER_SERVICE | support@exlibya.ly |

الحسابات التجريبية بلا مصادقة ثنائية افتراضيًا — أي حساب يستطيع تفعيلها بنفسه
عبر `POST /auth/mfa/setup` ثم `/confirm` إن أراد تجربتها (انظر قسم "المصادقة
الثنائية" أدناه)؛ ليست مفروضة على أي مسار حاليًا.

## الاختبارات

```bash
npm test          # اختبارات الوحدة
npm run test:cov  # مع تقرير التغطية
```

تغطي الاختبارات الحالية القواعد الحرجة على قاعدة الأعمال:

- **قاطع دائرة أسعار الصرف** (`src/fx-rates/rate-deviation.spec.ts`): رفض أي تغيّر
  سعر يتجاوز نسبة الانحراف المسموح بها دون سبب تجاوز موثّق، وقبوله مع تسجيله
  كتجاوز يدوي عند إرفاق السبب.
- **دفتر حركات الخزينة** (`src/treasury/treasury.service.spec.ts`): رفض أي سحب
  يتجاوز الرصيد الحالي، وصحة احتساب الرصيد بعد كل حركة.
- **تسعير الصفقات** (`src/deals/deal-pricing.spec.ts`): التحويل إلى ما يعادله
  بالدولار عبر آخر سعر دولار منشور، ورفض التسعير عند غياب سعر دولار منشور.
- **محرك التداول** (`src/deals/deals.service.spec.ts`): اعتماد كل صفقة فورًا
  بلا فحص حدود مهما كبر مبلغها، صحة احتساب `lockedRate`/`parallelMarketRate`/
  `profitLyd` من مدخلات يدوية بحتة (`dealRate`/`parallelMarketRate`) وتخزينها
  عند الإنشاء، ترحيل هامش الصفقة الصحيح (ربح/خسارة) إلى قائمة الدخل عند التنفيذ
  وتخطّيه كليًا عند هامش صفري، منع اعتماد أي صفقة تاريخية بانتظار موافقة
  (`PENDING_APPROVAL`) من نفس مَن أنشأها، وصفقة زبون خارجي كاملة (إنشاء بلا
  `clientId` ولا فحص KYC، رفض مزج `clientId` مع `externalCustomerName`، وتنفيذ
  يرسل تأكيد واتساب لهاتفه المُدخَل يدويًا أو لا يرسل شيئًا بلا رقم).
- **بوابة واتساب** (`src/whatsapp/*.spec.ts`): توجيه النوايا (استفسار سعر مقابل
  تحويل لموظف)، استخراج الرسائل النصية من حمولة Webhook الخام لـ Meta بأمان،
  التحقق من توقيع HMAC (رفض توقيع مزوَّر أو جسم مُعدَّل)، وصياغة كل رد/قالب —
  بما فيها إشعار رصيد العميل (`composeClientBalanceUpdateParams`، إشارة +/-
  الصحيحة حسب نوع الحركة). `TreasuryService`/`ClientsService` تتحقق بدورها من
  استدعاء `sendClientBalanceUpdate` بالمعطيات الصحيحة عند كل حركة مرتبطة بعميل
  (وعدم استدعائه إطلاقًا لحركة عادية بلا عميل).
- **المصادقة الثنائية** (`src/auth/mfa/*.spec.ts`, `src/auth/auth.service.spec.ts`):
  تطابق رموز TOTP مع متجهات اختبار RFC 6238 المرجعية، تشفير/فكّ سرّ TOTP
  (AES-256-GCM) ورفض مفتاح أو توقيع خاطئ، ودورة تسجيل الدخول الكاملة (رمز
  تحدّي بدل وصول مباشر، رفض رمز تحدّي كرمز وصول، استهلاك رمز الاسترداد مرة واحدة).
- **المصاريف التشغيلية** (`src/expenses/expenses.service.spec.ts`): رفض التسجيل
  على فرع أو عملة غير موجودة، ومنع إلغاء (void) مصروف ملغى بالفعل.
- **التقارير والتحليلات** (`src/reports/reports.service.spec.ts`): صحة احتساب
  صافي حركة الخزينة لكل عملة (حركات موجبة ناقص سالبة)، وتوزيع المصاريف حسب الفئة.

## القواعد التي ينفّذها الكود (لا التوثيق فقط)

- **لا حذف ولا تعديل على السجلات التراكمية**: `TreasuryMovement` و `ExchangeRate`
  و `AuditLog` جداول إضافة فقط (Append-only) — لا توجد في أي خدمة دالة `update`
  أو `delete` عليها. كل حركة خزينة تحمل `balanceAfter` في نفس الصف.
- **قاطع دائرة أسعار الصرف**: أي نشر سعر يتجاوز `FX_MAX_DEVIATION_PERCENT` (افتراضيًا
  8%) يُرفض ما لم يُرفَق بـ `overrideReason`، وعندها يُسجَّل السعر بمصدر `OVERRIDE`
  مع صاحبه وسببه في سجل التدقيق (`src/fx-rates/rate-deviation.ts`).
  انظر أيضًا `src/fx-rates/fx-rates.service.ts`.
- **الصلاحيات (RBAC)**: كل مسار حسّاس مقيّد بـ `@Roles(...)` — مثلًا نشر الأسعار
  وتعديل حدود العملاء مقصوران على `ADMIN`/`TREASURY_MANAGER`، وتحديث حالة KYC على
  `ADMIN`/`COMPLIANCE_OFFICER`.
- **الرصيد لا يصبح سالبًا**: `applyMovement` (`src/treasury/apply-movement.ts`) يرفض
  أي سحب، تحويل صادر، أو تسوية صفقة (طرف العملة الأجنبية أو طرف الدينار معًا)
  يتجاوز الرصيد الحالي قبل أي كتابة على قاعدة البيانات — سواء استُدعي من حركة
  يدوية أو من تنفيذ صفقة.
- **تنفيذ صفقة يحرّك خزينتَين لا واحدة**: `DealsService.execute` يسجّل حركتَي
  خزينة منفصلتَين لكل صفقة، ضمن معاملة واحدة — طرف العملة الأجنبية بكمية الصفقة
  (`TRADE_BUY`/`TRADE_SELL`، كما كان)، **وطرف الدينار الليبي المقابل** بقيمة
  `lydEquivalent` (= الكمية × سعر القفل — التسوية النقدية الفعلية مع العميل):
  `TRADE_BUY_SETTLEMENT` (نقصان: تُدفع للعميل) عند الشراء، أو
  `TRADE_SELL_SETTLEMENT` (زيادة: تُحصَّل منه) عند البيع. قبل هذا كانت خزينة
  الدينار لا تتأثر إطلاقًا بأي صفقة صرف رغم أن نقدًا حقيقيًا يتغيّر يدًا بيد مع
  كل صفقة — كلتا الحركتين الآن إلزاميتان لتنفيذ الصفقة: نقص رصيد الدينار عن
  قيمة التسوية المطلوبة يرفض التنفيذ بالكامل (تراجع تلقائي كامل، بلا تنفيذ
  جزئي)، تمامًا كنقص العملة الأجنبية نفسها. **يتطلب هذا وجود مركز خزينة دينار
  مفعَّل للفرع مسبقًا** (`POST /treasury/branches/:branchId/positions`) تمامًا
  كعملة الصفقة الأجنبية — لا يُنشأ تلقائيًا. (تبقى هذه الحركة تتبّعًا تشغيليًا
  لرصيد الخزينة الفعلي فقط، منفصلة عن دفتر الأستاذ الرسمي — انظر بند "فجوة
  معروفة" في قسم المحاسبة أدناه.)
- **قفل السعر مؤقت وصارم**: كل صفقة تحمل `lockExpiresAt` (60 ثانية من إنشائها).
  محاولة اعتمادها أو تنفيذها بعد انتهاء المهلة تُعلِّمها تلقائيًا `EXPIRED` وترفض
  العملية، بدل تنفيذها بسعر تجاوزه الزمن (`DealsService.expireIfLockPassed`).
- **لا موافقة مزدوجة ولا فحص حدود عند إنشاء الصفقة**: كل صفقة صحيحة البيانات
  تُنشأ معتمدة (`APPROVED`) مباشرة، مهما كان مبلغها أو حالة حدود العميل
  (`dailyLimitUsd`/`creditLimitUsd` تبقيان في نموذج بيانات العميل لأغراض أخرى،
  لكن `DealsService.create` لم يعد يفحصهما). مسارا `approve`/`reject` وحالة
  `PENDING_APPROVAL` أُبقيا في الكود لتسوية أي صفقة تاريخية دخلت هذه الحالة قبل
  هذا التغيير فقط — لا صفقة جديدة تدخلها.
- **حدود العميل اختيارية بالكامل الآن، وغير مطلوبة عند التسجيل**: `dailyLimitUsd`/
  `creditLimitUsd` أصبحا حقلين اختياريين (`Decimal?`) في نموذج العميل — `POST
  /clients` لم يعد يقبلهما إطلاقًا (لا معنى لهما وقت التسجيل بعد إلغاء أي فحص
  حدّي على الصفقات)، وتبقى `null` حتى يضبطهما مسؤول لاحقًا يدويًا عبر `PATCH
  /clients/:id/limits` إن أراد الاحتفاظ برقم مرجعي فقط لا لأي فحص فعلي.
- **سعر الصفقة وسعر السوق الموازي كلاهما يدوي بالكامل عند الإنشاء**: `lockedRate`
  (سعر الصفقة — حقل `dealRate` في الطلب) لم يعد يُشتَق تلقائيًا من آخر سعر صرف
  منشور؛ الموظف يُدخله يدويًا بنفسه، تمامًا كـ`parallelMarketRate` (سعر السوق
  الموازي) الذي كان يدويًا أصلًا. آخر سعر منشور (`sourceRateId`) يبقى مطلوب
  الوجود (تأكيدًا أن العملة متداولة فعليًا) لكنه مرجعي/للتدقيق فقط الآن، لا
  يُستخدم في احتساب `lockedRate` بتاتًا. `profitLyd` (الفرق بين السعرين مضروبًا
  بالكمية، بالدينار — `computeDealProfitLyd`) يُحسب ويُخزَّن فورًا: عند الشراء
  (BUY) الربح إن كان سعر السوق أعلى من سعر الصفقة، وعند البيع (SELL) الربح إن
  كان سعر الصفقة أعلى من سعر السوق. لا يُرحَّل هذا الهامش محاسبيًا إلا عند تنفيذ
  الصفقة فعليًا (`DealsService.execute`)، ضمن نفس معاملة تسوية الخزينة: مدين
  `FX_TRADING_MARGIN_RECEIVABLE`/دائن `FX_TRADING_REVENUE` عند ربح، والعكس عند
  خسارة (قيد صفري يُتخطّى كليًا) — فصفقة أُلغيت أو انتهت مهلتها لا تمسّ قائمة
  الدخل إطلاقًا.
- **صفقة لعميل داخلي مسجَّل أو لزبون خارجي عابر، بلا بيانات إضافية للخارجي**:
  `customerType` (`INTERNAL`/`EXTERNAL`) على غرار `Remittance.customerType` —
  عميل داخلي يتطلب `clientId` وحده (يخضع لفحص KYC كما كان). زبون خارجي **لا
  يتطلب أي بيانات أخرى** — أُلغي إدخال اسم وهاتف الزبون الخارجي صراحةً
  (`CreateDealDto` لا يقبلهما إطلاقًا الآن: `property externalCustomerName
  should not exist` عند محاولة إرساله، بفضل `forbidNonWhitelisted` على
  الـ ValidationPipe العام)؛ `customerType` وحده يكفي لتمييز الصفقة.
  `Transaction.externalCustomerName`/`externalCustomerPhone` أُبقيا في
  المخطط نفسه (عمودان اختياريان) للحفاظ على بيانات صفقات تاريخية سبقت هذا
  التغيير فقط — كل صفقة EXTERNAL جديدة تُخزَّن بهما `null` وتُعرَض بتسمية
  عامة "زبون خارجي" (`DealsService.dealPartyName`)؛ صفقة تاريخية قديمة يبقى
  اسمها الفعلي المحفوظ ظاهرًا. لا يُقبل `clientId` مع `EXTERNAL`. `clientId`
  عمود اختياري (`String?`) في `Transaction`؛ أي موظف مخوَّل
  (`TELLER`/`TREASURY_MANAGER`/`ADMIN`) ينشئ وينفّذ صفقة لأي طرف. تأكيد
  واتساب التنفيذ (`sendDealConfirmation`) يُرسَل فقط لعميل داخلي عبر هاتفه
  المسجَّل الآن عمليًا (زبون خارجي لم يعد له رقم مُدخَل، فلا شيء يُرسَل له —
  لا خطأ)؛ يبقى الفرع القديم في `WhatsAppService.sendDealConfirmation`
  والاختبارات يدعم هاتف زبون خارجي تاريخي إن وُجد، توافقًا رجعيًا فقط.
- **رقم معاملة تسلسلي قابل للقراءة لكل صفقة**: `Transaction.dealNumber`
  (`Int @unique`، يبدأ من `100001`) يولَّده تسلسل قاعدة بيانات مستقل
  (`transactions_dealNumber_seq`)، لا `id` (UUID الداخلي الذي تبقى عليه كل
  مسارات الـ API — تنفيذ/اعتماد/رفض/إلغاء). يُعرَض كعمود أول في جدول
  الصفقات بالواجهة، ويحلّ محل جزء الـ`id` المبتور (`#${id.slice(0,8)}`) في
  نصوص السبب/الوصف الداخلية (حركة الخزينة وقيد هامش الصفقة المحاسبي) —
  نص مقروء فعليًا بدل شظية Hex عشوائية. الصفقات الموجودة مسبقًا عُبِّئت
  بترتيب الإنشاء (الأقدم رقمه أصغر) عبر migration يدوي.
- **بحث حيّ عن العميل الداخلي في شاشة الصفقات**: حقل نصي (`deal-client-search`)
  يستعلم `GET /clients?search=...&pageSize=8` مباشرة (تأخير 300ms) بدل
  قائمة منسدلة ثابتة محدودة بصفحة العملاء المحمَّلة في الكاش محليًا — بحث
  فعلي بالاسم أو الهاتف عبر كامل قاعدة العملاء، لا الصفحة الأخيرة المعروضة
  فقط في تبويب العملاء.
- **التنفيذ ذرّي (atomic) وآمن من التزامن**: `DealsService.execute` يستخدم تحديثًا
  شرطيًا (`updateMany` بشرط الحالة) داخل معاملة واحدة تشمل أيضًا تحديث رصيد الخزينة،
  فلا يمكن تنفيذ الصفقة مرتين ولا تنفيذها جزئيًا.
- **رسالة واتساب فاشلة لا تكسر عملية مالية أبدًا**: كل دالة إرسال في `WhatsAppService`
  تلتقط استثناءات المزوّد داخليًا وتُسجّل الرسالة بحالة `FAILED` بدل رميها لأعلى —
  نشر سعر أو تنفيذ صفقة ينجحان دومًا بصرف النظر عن حالة واتساب (انظر اختبار
  "فشل بثّ واتساب لا يفسد نشر السعر نفسه" في `fx-rates.service.spec.ts`).
- **قوالب معتمدة إلزامية لأي رسالة تبدأها الشركة**: الردود على رسائل واردة (استفسار
  سعر، تحويل بشري) نص حر لأنها داخل نافذة خدمة مفتوحة للتو؛ أي رسالة تبدأها
  الشركة (بثّ سعر، تأكيد صفقة، تنبيه حد) تُرسل حصرًا كقالب معتمد (`WHATSAPP_TEMPLATES`).
- **توقيع Webhook مُتحقَّق منه**: `verifyMetaSignature` يقارن HMAC-SHA256 للجسم
  الخام بتوقيع رأس `X-Hub-Signature-256` بمقارنة زمن ثابت (`timingSafeEqual`) —
  أي حمولة موقّعة بسرّ خاطئ أو معدَّلة بعد التوقيع تُرفض.
- **رمز تحدّي المصادقة الثنائية لا يمنح أي صلاحية**: موقّع بنفس سرّ JWT لكن
  `JwtStrategy` يرفضه صراحة إن استُخدم كرمز Bearer عادي — لا يصلح إلا لمسار
  `/auth/mfa/verify` (انظر "يرفض رمز وصول عادي... كرمز تحدّي" في `auth.service.spec.ts`).
- **رمز الاسترداد أحادي الاستخدام فعليًا**: `AuthService.verifyMfa`/`disableMfa`
  يحذفان رمز الاسترداد المُستخدَم من `mfaRecoveryCodeHashes` فور نجاح التحقق —
  استخدامه مرة ثانية يُرفض.

## المصارف (حسابات بنكية مستقلة مركزيًا)

- **كيان مواز لخزينة الفرع، لا فرق جوهري بينهما**: `Bank`/`BankPosition`/
  `BankMovement` (`src/treasury/banks.service.ts`) تكرّر بنية `Branch`/
  `TreasuryPosition`/`TreasuryMovement` تمامًا — مركز رصيد لكل عملة (سقف
  تعرّض وحد أدنى تحذيري اختياريان) ودفتر حركات تراكمي (Append-only) يحمل
  الرصيد بعد كل حركة مباشرة. الفرق الوحيد: الحساب المصرفي **غير مرتبط بأي
  فرع** — مستقل مركزيًا، يمثّل حسابًا بنكيًا حقيقيًا للشركة لا موقعًا فعليًا
  للنقد.
- **نوع الحركة مقيَّد بمجموعة فرعية**: `RecordBankMovementDto` يقبل فقط
  `DEPOSIT`/`WITHDRAWAL`/`TRANSFER_IN`/`TRANSFER_OUT`/`ADJUSTMENT_INCREASE`/
  `ADJUSTMENT_DECREASE` (`@IsIn`، لا `@IsEnum(MovementType)` الكامل) —
  `TRADE_BUY`/`TRADE_SELL` وتسويتهما خاصة بتنفيذ صفقات الصرف على خزينة فرع،
  لا معنى لها على حساب مصرفي مجرَّد.
- **التحويل بين خزينة فرع وحساب مصرفي حركتان مستقلتان تمامًا، بلا ربط بنيوي**:
  على غرار التحويل بين فرعين حاليًا — `TRANSFER_OUT` على الفرع ثم
  `TRANSFER_IN` على المصرف (أو العكس)، كل واحدة تُسجَّل عبر مسارها الخاص
  ضمن معاملتها المستقلة؛ لا حقل يربط إحداهما بالأخرى في قاعدة البيانات،
  فقط نص السبب يدويًا (قرار تصميم صريح: تفضيلًا للبساطة على الذرّية بين
  الفرع والمصرف، بخلاف حركتَي تسوية الصفقة الواحدة اللتين تبقيان ضمن
  معاملة واحدة إلزامًا).
- **الترحيل المحاسبي**: `BANK_CASH` (الرمز `1015`) كان سابقًا حسابًا صوريًا
  يمثّل "البنك" كطرف خارجي مبهم لحركات إيداع/سحب الفرع العادية (`TILL_CASH`
  مقابل `BANK_CASH`) بلا أي مصرف حقيقي خلفه؛ الآن أصبح حسابًا حقيقيًا
  (المجموع الفعلي لكل مراكز `BankPosition`) — حركة مصرف تُرحِّل قيدًا بين
  `BANK_CASH` (طرف المصرف نفسه) وحساب مقابل يعتمد على النوع:
  `TRANSFER_IN`/`TRANSFER_OUT` يستخدمان `INTER_BRANCH_CLEARING` (الرمز
  `1030`، وسِّع اسمه من "بين الفروع" ليشمل تسويات فرع↔مصرف أيضًا) — نفس
  حساب العبور الذي يستخدمه طرف الفرع في نفس التحويل فيتوازنان معًا؛
  `DEPOSIT`/`WITHDRAWAL` (أموال خارجية حقيقية لا تمر بخزينة فرع، كتحويل
  وارد من مراسل أو رسوم بنكية) يستخدمان حسابًا جديدًا `EXTERNAL_FUNDS_CLEARING`
  (الرمز `1035`) بدل `BANK_CASH` نفسه (لا يصح أن يكون طرفا القيد نفس
  الحساب)؛ `ADJUSTMENT_INCREASE`/`ADJUSTMENT_DECREASE` يستخدمان نفس حسابَي
  فروقات جرد الفرع (`CASH_OVER_INCOME`/`CASH_SHORT_EXPENSE`).
- **مقصورة على `ADMIN`/`TREASURY_MANAGER` بالكامل** — لا `TELLER`، خلافًا
  لحركات خزينة الفرع التي يسجّلها الصرّاف أيضًا: قرار عمل صريح أن الحسابات
  المصرفية إدارة خزينة عليا لا عمل شباك يومي.
- **بلا ربط بعميل إطلاقًا**: خلافًا لحركة خزينة الفرع، لا يقبل
  `RecordBankMovementDto` حقل `clientId` — لا معنى لعميل يودع/يسحب مباشرة
  من حساب مصرفي للشركة.
- **حماية من الحذف الفعلي**: تعطيل حساب مصرفي (`PATCH
  /treasury/banks/:id/status`) يخفيه من كل قوائم الاختيار التشغيلية دون
  فقدان أي مركز أو حركة تاريخية مرتبطة به — تمامًا كتعطيل فرع.
- **تحقّقت من كل ما سبق فعليًا على قاعدة بيانات حقيقية**: إنشاء حساب
  مصرفي، رفض تكرار الرمز، رفض حركة قبل تفعيل خط العملة، رفض نوع حركة غير
  مسموح (`TRADE_BUY`)، رفض `TELLER` تسجيل حركة مصرف (403)، تحويل فعلي بين
  فرع وحساب مصرفي بحركتين مستقلتين مع التحقق من توازن القيدين المحاسبيين
  الناتجين ومن أن الميزانية العمومية تبقى متوازنة (`balanceCheck.difference
  = 0.00`) بعدها.

## بوابة واتساب (WhatsApp Business Cloud API)

- **بلا بيانات اعتماد Meta محليًا**: إن كانت `WHATSAPP_ACCESS_TOKEN` أو
  `WHATSAPP_PHONE_NUMBER_ID` فارغتين، يفعّل `WhatsAppModule` تلقائيًا
  `NullWhatsAppProvider` الذي يسجّل الرسائل في السجلات دون إرسالها فعليًا — فتعمل
  بقية المنظومة (توجيه النوايا، سجل الرسائل، التنبيهات التلقائية) كاملةً محليًا
  دون حساب Meta حقيقي.
- **الربط الخلفي (Webhook)**: `GET /webhooks/whatsapp` للتحقق الأولي من الرابط في
  Meta Business Manager، و`POST /webhooks/whatsapp` لاستقبال الرسائل — كلاهما
  عام (`@Public()`) لأن Meta لا يرسل رمز JWT، ويعتمدان بدل ذلك على `WHATSAPP_VERIFY_TOKEN`
  و`WHATSAPP_APP_SECRET` على التوالي.
- **السيناريوهات الآلية المطبَّقة**: استفسار سعر فوري (رد نصي فوري بالأسعار الحالية)،
  تحويل لموظف بشري (إقرار فوري)، تأكيد تنفيذ صفقة (قالب، تلقائي من `DealsService.execute`)،
  **إشعار رصيد تلقائي بعد كل حركة على رصيد وديعة عميل** (قالب `CLIENT_BALANCE_UPDATE`،
  تلقائي من `TreasuryService.recordMovement` عند الربط بعميل، ومن
  `ClientsService.adjustBalance`، بعد نجاح الحركة فعليًا لا قبله — انظر قسم رصيد
  وديعة العملاء أدناه)، وبثّ تحديث سعر جماعي للمشتركين (`whatsappOptIn`) — تلقائي
  عند تجاوز الانحراف `WHATSAPP_BROADCAST_DEVIATION_PERCENT`، أو يدوي عبر
  `POST /whatsapp/broadcast/:currencyCode`. (تنبيه اقتراب من حد العميل عبر
  `WhatsAppService.sendLimitAlert` يبقى مبنيًّا وجاهزًا في الكود، لكن لم يعد أي
  مسار يستدعيه بعد إلغاء فحص حدود العميل عند إنشاء الصفقة.)

## المصادقة الثنائية (TOTP)

- **تنفيذ من الصفر بلا مكتبة خارجية**: HOTP/TOTP (RFC 4226/6238) وBase32 مبنيّان
  فوق وحدة `crypto` المدمجة في Node فقط (`src/auth/mfa/`) — أُثبتت صحتهما بمقارنة
  مباشرة مع متجهات اختبار RFC 6238 المرجعية، لا بإعادة تنفيذ المرجع نفسه.
- **تدفّق تسجيل الدخول**: `POST /auth/login` يعيد `accessToken` مباشرة لحساب بلا
  مصادقة ثنائية، أو `mfaChallengeToken` قصير الأجل (5 دقائق) لحساب مفعّل عليها؛
  `POST /auth/mfa/verify` يستبدله برمز وصول كامل بعد تأكيد رمز TOTP أو رمز استرداد.
- **الإعداد الذاتي**: `POST /auth/mfa/setup` (يعيد السرّ ورابط QR) ثم
  `POST /auth/mfa/confirm` (بأول رمز صحيح) يفعّلان المصادقة ويولّدان 8 رموز
  استرداد أحادية الاستخدام؛ `POST /auth/mfa/disable` يعطّلها.
- **الإلزامية اختيارية بالكامل**: `@RequireMfa()` و`MfaGuard` مبنيّان وجاهزان
  (مختبَران في `src/common/guards/mfa.guard.ts`) لكن غير مطبَّقين على أي مسار
  حاليًا — قرار تفعيلها على إجراء بعينه (نشر سعر مثلًا) يُترك للمشغّل حسب سياسته
  الأمنية؛ فعّلها بإضافة `@RequireMfa()` فوق أي معالج مسار.

## إدارة المستخدمين والصلاحيات

- **مقصورة بالكامل على ADMIN**: `UsersController` بأكمله مقيَّد بـ `@Roles(ADMIN)`
  على مستوى الكلاس — لا مسار واحد فيه متاح لأي دور آخر، خلافًا لبعض الوحدات
  الأخرى التي تتيح القراءة للجميع وتحصر الكتابة فقط. المستخدمون قبل هذه الوحدة
  كانوا يُنشَؤون حصرًا عبر `prisma/seed.ts` مباشرة على قاعدة البيانات — الآن
  عبر لوحة تحكم كاملة (بطاقة "المستخدمون والصلاحيات" ضمن تبويب الإعدادات).
- **`POST /users`**: تسجيل مستخدم جديد بالاسم والبريد وكلمة مرور مبدئية (8 أحرف
  على الأقل) ودور وظيفي (`StaffRole`) وفرع اختياري. لا بريد تلقائي يرسل كلمة
  المرور بعد — يُبلَّغ المستخدم بها يدويًا عبر قناة آمنة خارج النظام.
- **`GET /users`**: قائمة بفلترة بالدور والحالة (`isActive=true/false`) وبحث
  بالاسم أو البريد، مع ترقيم صفحات. **لا يُعاد `passwordHash` ولا حقول
  المصادقة الثنائية الحسّاسة في أي استجابة من هذه الوحدة إطلاقًا** — `select`
  صريح دومًا (`SAFE_USER_SELECT`).
- **`PATCH /users/:id/role`**: تغيير الدور الوظيفي والفرع الثابت معًا، بسبب
  موثَّق إلزامي يُحفظ في سجل التدقيق. حقل الفرع الفارغ يعني إلغاء أي ارتباط
  بفرع صراحةً، لا الإبقاء على القديم.
- **`PATCH /users/:id/status`**: تفعيل/تعطيل حساب — حساب معطَّل لا يستطيع صاحبه
  تسجيل الدخول (`AuthService.login` يرفضه) حتى لو كانت بياناته صحيحة، بلا حذف
  فعلي لسجله التاريخي.
- **`PATCH /users/:id/reset-password`**: إعادة تعيين كلمة مرور مستخدم مباشرة
  (نسيان، أو تسوية أمنية) — بسبب موثَّق إلزامي أيضًا.
- **حراسة صريحة ضد قفل النظام بلا أي مدير** (`UsersService`، سيناريو حسّاس
  حقيقي لا نظري): (١) لا يجوز لمستخدم تعديل دوره الوظيفي أو تعطيل حسابه هو
  نفسه بنفسه — `ForbiddenException` فورية، يجب أن يطلب ذلك من مدير نظام آخر؛
  (٢) لا يجوز تعطيل حساب آخر `ADMIN` فعّال في النظام ولا تنحيته عن دوره إلى
  دور آخر — `ConflictException` تمنع العملية ما لم يوجد `ADMIN` آخر فعّال
  غيره أولًا. كلا الفحصين مختبَران صراحةً وتحقّقتُ منهما يدويًا على قاعدة
  بيانات حقيقية (ترقية مستخدم إلى ADMIN ثانٍ، تعطيل الأول بنجاح، ثم رفض تعطيل
  الثاني بصفته آخر ADMIN فعّال متبقٍّ).

## رصيد وديعة العملاء (Custody)

- **منفصل تمامًا عن تسوية الصفقات الفورية عند الشباك**: `ClientBalance` يمثّل ما
  يحتفظ به العميل كوديعة لدى الشركة نفسها (لا علاقة له بصفقات الصرف الفورية التي
  تُسوَّى نقدًا مباشرة). دفتر تراكمي غير قابل للتعديل (`ClientBalanceMovement`) يحفظ
  كل حركة برصيدها بعدها مباشرة — بلا أي `UPDATE`/`DELETE` على مستوى التطبيق، تمامًا
  كسجل `TreasuryMovement`.
- **إيداع/سحب مرتبط بخزينة فرع (اختياري)**: `POST /treasury/branches/:branchId/movements`
  يقبل حقل `clientId` اختياريًا — لا يُقبل إلا مع نوع `DEPOSIT` أو `WITHDRAWAL`. عند
  تمريره، تُحدَّث خزينة الفرع **ورصيد وديعة العميل** معًا ضمن معاملة واحدة (نفس نمط
  `Expense.paidFromTreasury`)؛ عدم تمرير `clientId` يُبقي الحركة حركة خزينة عادية
  بلا أي أثر على أرصدة العملاء.
- **الرصيد يُسمح له أن يصبح سالبًا عمدًا**: خلافًا لرصيد خزينة الفرع (`applyMovement`
  يرفض أي رصيد سالب)، `applyClientBalanceMovement` يسمح صراحةً بعميل مدين — تعرضه
  الواجهة بالأحمر ("مدين") بدل رفض العملية، تمامًا كما هو مطلوب لعميل عليه التزام
  تجاه الشركة.
- **تصحيح يدوي منفصل**: `POST /clients/:id/balance-adjustments` (مقيّد بـ
  `ADMIN`/`TREASURY_MANAGER`، يتطلب سببًا موثّقًا لا يقل عن 10 أحرف) يصحّح رصيد
  العميل مباشرة بلا أي أثر على خزينة أي فرع — لتصحيح أخطاء إدخال سابقة أو تسويات
  إدارية فقط، لا للإيداع/السحب الفعلي (ذاك يمر عبر حركة الخزينة أعلاه).
- **`GET /clients/:id/balance-movements`**: سجل حركات رصيد عميل (إيداع/سحب/تعديلات)،
  الأحدث أولًا، اختياريًا مفلترًا بعملة واحدة (`currencyCode`)؛ يضمّ كل صف أحدث
  إشعار واتساب مرتبط به (`whatsappMessages`، صف واحد على الأكثر عمليًا) لتعرض
  الواجهة حالة تسليمه (أُرسل/فشل/—) بجانب الحركة مباشرة.
- **إشعار واتساب تلقائي بالرصيد الجديد بعد كل حركة**: `WhatsAppService.sendClientBalanceUpdate`
  (قالب `CLIENT_BALANCE_UPDATE`) يُستدعى تلقائيًا بعد نجاح أي حركة على رصيد
  وديعة عميل — سواء إيداع/سحب فعلي عبر خزينة فرع أو تصحيح يدوي — بصرف النظر عن
  `whatsappOptIn` (إشعار معاملاتي شخصي بنتيجة فعل يخصّ العميل نفسه، لا بثّ
  تسويقي جماعي؛ نفس مبدأ `sendDealConfirmation`). يُستدعى بعد نجاح الحركة فعليًا
  خارج معاملة قاعدة البيانات (على غرار تنفيذ الصفقات)، وفشله لا يكسر الحركة
  المالية أبدًا — يُسجَّل بحالة `FAILED` في `WhatsAppMessage` (مرتبطًا بالحركة
  عبر `relatedClientBalanceMovementId`) بدل رميه لأعلى.

## المصاريف التشغيلية والتقارير المالية

- **المصاريف منفصلة تمامًا عن خزينة العملاء**: `POST /expenses` يسجّل مصروف تشغيل
  الشركة نفسها (رواتب، إيجار، كهرباء، أتعاب مهنية...) بفئة (`ExpenseCategory`)
  ومبلغ وعملة ووصف، واختياريًا فرع مرتبط — لا يُنشئ أو يعدّل أي `TreasuryMovement`
  ولا يمسّ رصيد الخزينة إطلاقًا. مقيّد بـ `ADMIN`/`TREASURY_MANAGER`.
- **لا حذف فعلي**: تصحيح مصروف مسجَّل بالخطأ يكون بإلغائه (`POST /expenses/:id/void`)
  مع سبب موثّق — يبقى ظاهرًا في القوائم (بعلامة `isVoided`) وفي سجل التدقيق، لا يُحذف.
- **`GET /expenses`**: فلترة بالفئة، الفرع، الفترة الزمنية (`from`/`to`)، مع ترقيم
  صفحات؛ يستثني المصاريف الملغاة افتراضيًا (`includeVoided=true` لإظهارها).
- **`GET /reports/summary`**: ملخص مالي شامل لفترة (الشهر الحالي افتراضيًا) —
  حجم الصفقات المنفَّذة وعددها، إجمالي المصاريف لكل عملة، صافي حركة الخزينة لكل
  عملة (مجموع الحركات الموجبة ناقص السالبة)، عدد العملاء الجدد، والصفقات المعلَّقة.
- **`GET /reports/expenses-by-category`**: توزيع المصاريف حسب الفئة — مادة جاهزة
  لرسم بياني دائري في الواجهة.
- **`GET /reports/deals-trend`**: حجم الصفقات المنفَّذة يوميًا خلال فترة (استعلام SQL
  مباشر بـ `date_trunc`) — مادة جاهزة لرسم بياني خطي.
- **`GET /reports/treasury-consolidated`**: إجمالي أرصدة الخزينة عبر كل الفروع لكل
  عملة — لقطة الوضع الحالي، بلا فترة زمنية. كل مسارات `/reports` مقيّدة بـ
  `ADMIN`/`TREASURY_MANAGER`/`COMPLIANCE_OFFICER`.

## الحوالات (وسترن يونيون / موني جرام)

- **وحدة مستقلة تمامًا**: الشركة وكيل تحويل أموال لشبكتَي وسترن يونيون وموني
  جرام (`RemittanceProvider`)؛ لا علاقة لهذه الوحدة بحسابات وديعة العملاء
  (`ClientBalance`) ولا بحركات خزينة الفروع — سجل ربح/تكلفة مستقل بذاته.
- **تصنيف العميل إلزامي لكل حوالة**: `customerType` إما `INTERNAL` (عميل مسجَّل
  في النظام — `clientId` إلزامي وحده) أو `EXTERNAL` (زبون عابر — اسمه يُدخَل
  يدويًا عبر `externalCustomerName` وحده)؛ مزج الاثنين أو تركهما فارغين مرفوض.
- **الاتجاه**: `SEND` (العميل يرسل عبر الشركة) أو `RECEIVE` (العميل يستلم) —
  مع اسم الطرف الآخر (`counterpartyName`) ورقم مرجعي إلزامي (`referenceNumber`:
  MTCN لوسترن يونيون أو الرقم المرجعي لموني جرام) لضمان تتبّع كل حوالة.
- **الربح يُحسب تلقائيًا ويُخزَّن عند التسجيل**: `profit = saleValue - cost`
  (لا يُعاد حسابه لاحقًا ولا يتغيّر إلا بإلغاء الحوالة كاملة) — يُسمح بربح سالب
  دون رفض العملية (لا يُفترض أن البيع دومًا أعلى من التكلفة).
- **لا حذف فعلي**: تصحيح حوالة مسجَّلة بالخطأ يكون بإلغائها
  (`POST /remittances/:id/void`) مع سبب موثّق — تبقى ظاهرة في القوائم والتقارير
  بعلامة `isVoided`، لا تُحذف. التسجيل مقيّد بـ `ADMIN`/`TREASURY_MANAGER`/`TELLER`؛
  الإلغاء بـ `ADMIN`/`TREASURY_MANAGER` فقط.
- **`GET /remittances`**: فلترة بالشبكة، الاتجاه، تصنيف العميل، الفرع، العميل،
  الفترة الزمنية — مع ترقيم صفحات، ويستثني الحوالات الملغاة افتراضيًا.
- **`GET /remittances/summary`**: ملخص أداء الوحدة لفترة — عدد الحوالات، إجمالي
  التكلفة، إجمالي قيمة البيع، والربح الصافي، مجمَّعة حسب الشبكة والاتجاه والعملة؛
  مقيّد بـ `ADMIN`/`TREASURY_MANAGER`/`COMPLIANCE_OFFICER`.

## المحاسبة العامة (دفتر أستاذ بالقيد المزدوج والقوائم المالية)

- **دفتر أستاذ حقيقي، لا تقرير مُجمَّع**: `Account` (شجرة حسابات)، `JournalEntry`
  و`JournalLine` (قيود اليومية) — كل قيد يتحقق `postJournalEntry` من توازنه
  **لكل عملة على حدة** (لا يكفي أن يتساوى الإجمالي عبر عملات مختلفة، ذلك لا
  يعني شيئًا محاسبيًا) قبل ترحيله؛ القوائم المالية تُشتَق حصرًا بتجميع (aggregate)
  هذا الدفتر، فتوازن معادلة "الأصول = الخصوم + حقوق الملكية" **مضمون بنيويًا**
  لا بأي تصحيح لاحق — طالما كل قيد مُرحَّل متوازن، وهو ما يتحقق منه الكود دومًا.
- **شجرة حسابات مزروعة تلقائيًا** (`ensureChartOfAccounts`, idempotent):
  نقدية الفروع، نقدية الحساب المصرفي، ذمم هامش الحوالات، ذمم هامش صفقات الصرف
  (`FX_TRADING_MARGIN_RECEIVABLE`) وإيراد الصرف المقابل (`FX_TRADING_REVENUE`)،
  أصول ثابتة (أثاث، سيارات، عقارات) ومجمع إهلاكها، وديعة العملاء المستحقة، ذمم
  دائنة، قروض طويلة الأجل، رأس المال، وحساب إيراد/مصروف مستقل لكل فئة مصروف
  (`ExpenseCategory`).
- **ترحيل تلقائي من الوحدات الأخرى** ضمن نفس معاملة كل عملية (لا خطوة منفصلة
  قد تفشل جزئيًا): تسجيل/إلغاء مصروف (`ExpensesService`)، حركة خزينة عادية أو
  مرتبطة برصيد عميل (`TreasuryService.recordMovement`)، تسجيل/إلغاء حوالة
  (هامش الحوالة يُرحَّل بثلاثة أسطر تُظهر الإيراد والتكلفة منفصلين، لا صافيًا
  فقط)، تنفيذ صفقة صرف (`DealsService.execute` يُرحِّل هامش الصفقة فقط — لا
  كامل قيمتها — بقيد بسطرين، ويتخطّاه كليًا إن كان الهامش صفرًا)، وتصحيح رصيد
  عميل يدوي (`ClientsService.adjustBalance`).
- **لا حذف ولا تعديل لأي قيد أبدًا**: تصحيح خطأ يكون بعكس القيد
  (`POST /accounting/journal-entries/:id/reverse`) — قيد جديد يبادل كل مدين
  بدائن، يشير لأصله عبر `reversalOfId`؛ يُرفض عكس قيد معكوس بالفعل.
- **`POST /accounting/journal-entries`**: ترحيل يدوي (مقيّد بـ
  `ADMIN`/`TREASURY_MANAGER`) لكل ما لا تستطيع الوحدات الأخرى ترحيله تلقائيًا
  بثقة: رأس المال، شراء/إهلاك الأصول الثابتة، القروض، الضريبة. (هامش صفقات
  الصرف نفسه يُرحَّل تلقائيًا الآن من `DealsService.execute` — لا حاجة لترحيله
  يدويًا هنا.)
- **فجوة معروفة: كامل قيمة الصفقة (لا هامشها فقط) غير ممثَّلة في دفتر الأستاذ**.
  `postJournalEntry` يرفض بنيويًا أي قيد يبادل عملة بأخرى (يتحقق من توازن كل
  عملة **على حدة** — انظر أعلاه)، فتبادل «دولار مقابل دينار» الكامل يحتاج حساب
  مقاصة عملات (FX clearing) غير موجود بعد؛ لذا يُرحَّل هامش الصفقة فقط محاسبيًا
  (أعلاه)، بينما القيمة الكاملة تبقى متتبَّعة تشغيليًا في `TreasuryPosition`/
  `TreasuryMovement` وحدهما (كلتا الخزينتين معًا منذ الإصلاح أعلاه)، لا في
  `Account`/`JournalEntry`. أثر ذلك عمليًا: `TILL_CASH` في قائمة المركز المالي
  لا يعكس فعليًا رصيد خزينة أي فرع الحقيقي بالعملات المتداولة في صفقات — فقط ما
  مرّ عبر `TreasuryService.recordMovement`/`ExpensesService` مباشرة.
- **`GET /accounting/balance-sheet`**: قائمة المركز المالي عند لحظة (`asOf`)
  اختياريًا لفرع واحد — أصول متداولة/ثابتة، خصوم متداولة/طويلة الأجل، حقوق
  الملكية (تشمل بند "الأرباح المرحّلة ونتيجة الفترة الحالية" محسوبًا لحظيًا من
  صافي الإيراد ناقص المصروف منذ إنشاء الدفتر — لا إقفال دوري يدوي)، مع
  `balanceCheck.difference` الذي يجب أن يكون صفرًا دومًا.
- **`GET /accounting/income-statement`**: قائمة الدخل لفترة — الإيرادات
  والمصاريف مفصَّلة حسب الحساب، صافي الربح قبل الضريبة، ثم بعدها إن رُحِّلت أي
  حركة لحساب "ضريبة الدخل" (5200) يدويًا.
- **إجمالي إرشادي بالدينار**: كل بند مُصنَّف بعملته الأصلية أولًا، ثم يُترجَم
  لإجمالي بالدينار بأحدث سعر صرف منشور — عملة بلا سعر منشور تُستثنى من
  الإجمالي (تبقى ظاهرة في التفصيل بعملتها) بدل افتراض سعر غير حقيقي.
- **`GET /accounting/journal-entries`**: دفتر اليومية الكامل، فلترة بالفترة/رمز
  الحساب/نوع المصدر، مع ترقيم صفحات. `GET /accounting/accounts`: شجرة الحسابات.
- واجهة كاملة قابلة للطباعة: القوائم المالية بتنسيق واضح مع زر "طباعة" لكل
  قائمة على حدة، نموذج ترحيل قيد يدوي بمعاينة توازن لحظية لكل عملة، ودفتر
  يومية بفلاتر وزر عكس لكل قيد.

## ما لم يُبنَ بعد (المرحلة التالية)

- **الأصول الثابتة كسجل تفصيلي (Fixed Asset Register)**: الحسابات موجودة في
  الشجرة وتُرحَّل إليها يدويًا، لكن لا يوجد بعد نموذج `FixedAsset` مستقل بتاريخ
  الشراء والعمر الإنتاجي واحتساب إهلاك دوري تلقائي — الإهلاك يُرحَّل يدويًا الآن.
- **إقفال دوري رسمي (Period Close)**: لا يوجد إجراء إقفال شهري/سنوي يُصفّر
  حسابات الإيراد والمصروف ويرحّلها لحساب الأرباح المرحّلة — النظام يعرضها حيًّا
  (صافي الإيراد ناقص المصروف منذ إنشاء الدفتر) بدل ذلك، وهو أسلوب شائع في
  الأنظمة المحاسبية الحديثة، لكنه لا يمنع لاحقًا إضافة إقفال رسمي إن احتيج له.
- **أنواع رسائل واتساب الأخرى**: الصور والمرفقات والردود السريعة (Interactive
  Buttons) خارج نطاق هذا الإصدار — يُعالَج النص فقط.
- **فرض المصادقة الثنائية**: غير مفروضة على أي مسار حاليًا (انظر قسم المصادقة
  الثنائية أعلاه) — تفعيلها على إجراء بعينه (نشر سعر مثلًا) قرار تشغيلي يُترك
  للمشغّل، بإضافة `@RequireMfa()` فوق المعالج المطلوب.
- **موافقة على المبالغ الكبيرة**: لا مصاريف ولا صفقات تخضع لموافقة مزدوجة حاليًا
  — التسجيل والاعتماد في الحالتين مباشران؛ قد يُضاف لاحقًا حد مبلغ يستوجب اعتماد
  `ADMIN` قبل أي `TREASURY_MANAGER` لأي منهما.
- **اختبارات التكامل (e2e)** مقابل قاعدة بيانات حقيقية (الاختبارات الحالية اختبارات
  وحدة بمحاكاة Prisma؛ التحقق مقابل قاعدة بيانات حقيقية جرى يدويًا أثناء التطوير).
